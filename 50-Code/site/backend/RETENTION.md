# Controlled retention & orphan file cleanup
There is no automatic user-data deletion until owner/legal review. The separately versioned \`backend/scripts/prune.ts\` is DRY RUN unless \`CONFIRM_DELETE=YES\`, \`RETENTION_DAYS\` is an owner-approved integer >=30, and the owner/migration DB connection plus private upload root are present. It removes only closed/won/lost inquiries older than the approved interval, followed by their UUID upload folders and orphan UUID folders after successful DB deletions. **Review a backup and run dry-run first**. Never enable cron without owner approval. This action is irreversible.

The daily private PostgreSQL backup job verifies custom dump format. On Sunday it attempts a full restore into a scratch database, checks \`schema_migrations\`, and drops the scratch database afterward. This weekly procedure is source-configured, **not yet run on the user's VPS**. Upload objects need separate encrypted and offsite backups; PostgreSQL dumps alone do not contain uploads.

For an isolated manual restore, stop only this staging application's API if necessary, use a new scratch DB, run \`pg_restore --no-owner --no-acl -d <scratch_db> <backup_file>\`, inspect \`rfq_inquiries\` / \`schema_migrations\`, and verify private file metadata against a secure copy of the private upload volume. Never restore into another application's production database.
